## 0. 한 장 요약

- 아마존 일본(JP) 셀러. 리스팅 약 27,000 · 하루 새 등록 30~40 상품군(100~130 SKU) · FBM(한국 발송).
- **구글 스프레드시트 하나에 붙은 Apps Script 프로젝트 하나**가 전부다. 아마존 광고 API v3(Sponsored Products) 와 SP-API 를 부른다. 서버·DB 없음.
- 광고는 **프로그램 셋**이 나눠 맡는다. 한 SKU 는 한 프로그램만 갖는다(소유권).

| 프로그램 | 대상 | 무엇을 하나 | 돈의 원칙 |
|---|---|---|---|
| 🆕 **신규 상품** (NEW_ADS, `78*`) | 새로 등록된 모든 상품군 | 싸게 근거를 만든다 — "팔리나" 만 본다. 근거가 쌓이면 🔁 에 넘긴다 | 상품군당 판돈(≤ ¥1,000) 안에서만 잃는다 |
| 🔁 **기존 광고** (EXPAND, `72AA~72AH`) | 이미 광고 중인 모든 SKU | 멈춤 · 감액 · 증액 시험(사다리) · 승격(가격선 캠페인) | 손해 불허. 올리는 것은 사람 승인 |
| 🌱 **새 상품 키우기** (옛 트랙 B, `72O·72S·72Y·72V·72W`) | 사람이 고른 몇 개 | 일부러 정한 만큼 손해를 보며 키워드 순위를 산다 | 주간허용손해 × 손해배수 안에서 |

- 공통 기반: 수집(`72_`, `72D`, `72R`, `72AC`, `72L`) · 실행/대장(`72J`, `72F`, `72K`) · 관제(`72N`) · 현황/그래프(`72U`, `72V_광고통계`) · 일정(`72X`) · 정책(`72Q`).
- **매일 트리거 19개**가 00~14시에 차례로 돈다 (§4). 사람이 매주 할 일은 🔁 후보 승인 하나다.
- 이 저장소의 `apps-script/` 는 Apps Script 프로젝트의 **거울**이다. 실행되는 원본은 Apps Script 쪽. 배포 방법은 §8.

## 1. 지켜야 할 것 (사용자 제약 — 새 설계도 지킨다)

1. **[사용자] 돈이 나가는 것은 명시적 승인.** 신규·확대는 설정/기준의 `모드 = 자동운영` 이 승낙이고, 키우기는 `광고육성` 의 [승인] 체크, 기존 광고의 멈춤·감액·증액은 `광고확대후보` 의 [승인] 체크. 승인 없이 돈이 나가는 경로를 만들지 않는다.
2. **[사용자] 비어 있는 *필수* 돈 한도는 '무제한' 이 아니라 '멈춤'.** (예외: 사용자가 명시적으로 위임한 신규 기본값 §2.1, 확대의 몇 한도.)
3. **[사용자] 수익을 내는 광고는 끄지 않는다.** 판돈·한도는 손실만 막는다. 성숙 주문이 하나라도 있으면 '위험 손실' 로만 잰다.
4. **[사용자] 한도·마진을 지어내지 않는다.** 마진율 원장은 바깥 시트 `광고 기준값` 탭. 없으면 원가 → 소싱 조달비 순 (`72AA`). 사람이 적은 값은 덮어쓰지 않는다.
5. **[사용자] API 키 · OAuth 비밀 · 리프레시 토큰은 기획서·시트·로그·커밋 어디에도 적지 않는다.** 전부 Apps Script 스크립트 속성에만.
6. **[사용자] 바깥 소싱 시트(`상품 목록` 탭)는 읽기 전용.** 예외 하나: 리프라이싱이 판매가를 바꾸면 그 줄의 판매가·마진을 따라 고친다 (`64B`).
7. **[사용자] 수집과 실행을 가른다.** 판단 단계에서 API 를 읽지 않는다 (6분 한도). 실행은 시트를 읽고 API 에 쓴다.
8. **[사용자] 줄임말 금지.** 시트 머리글도 말로. 커밋·코드 주석에 AI 모델 이름을 적지 않는다.
9. **[사용자] 한 SKU 는 한 곳에서만 입찰.** 프로그램이 SKU 를 새 캠페인에 넣으면 옛 그룹의 그 광고는 멈춘다 (지우지 않는다). 사람이 손으로 만든 수동 캠페인의 광고도 예외가 아니었다 — §9.3 참고.
10. 아마존 ID 는 자릿수 큰 숫자꼴 문자열. 시트가 숫자로 바꾸면 뒷자리가 반올림돼 **다른 ID** 가 된다. ID 칸은 반드시 글자 서식 `@`.

## 2. 세 프로그램의 의도

### 2.1 🆕 신규 상품 (NEW_ADS) — `78_신규광고.gs` `78B~78F`

**목적.** 새로 등록되는 상품 전부에, 상품군마다 판돈 하나를 걸고 "팔리나" 를 싸게 본다. 노출을 더 주는 것은 이 프로그램의 일이 아니다 — 근거가 쌓이면 🔁 에 소유권을 넘기고 손을 뗀다. 기획서 `docs/신규광고_기획서_NEW-ADS.md`.

**자료는 별도 파일에.** 운영 시트가 셀 한도의 절반을 써서, 신규의 표는 별도 스프레드시트 **"Amazon 신규 상품 광고"** (ID 는 운영 시트 `광고기준` 의 `[신규 · 자료 파일 ID]`) 에 둔다. 탭: `설정` · `상품통합` · `상품군광고` · `신규광고일별` · `서빙상태`. 운영 시트에는 계획 줄(`광고생성계획`, 트랙 N)만 온다.

**흐름 (매일).**
```
10:57 ① 가져오기 (78B naImportRun_)   소싱 시트 [상품 목록] → 새 SKU 읽기 → 상품군(끝 -\d+ 를 뗀 키)으로 묶기
                                        → 마진(72AA) → G(주문당 공헌이익) · q(판단주문율) · 허용입찰 · 시작입찰
                                        → 대표 옵션 하나 고르기 → 배분: 소액자동시작 / 옵션대기 / 정보대기 / 광고제외
11:00 ② 시작 (78C naRunStep_)         배분이 소액자동시작인 상품군을 가격선 풀 캠페인 'KP NEW B{k}-{n}' 에
                                        1 SKU = 1 광고그룹(자동 겨냥 4) 으로 넣는다. 풀 하나 20 그룹.
                                        만들기는 공용 실행(72J) 이 트랙 N 만 골라 한다. 시간 되면 3분 뒤 이어감.
                                        만든 뒤 풀 일예산 = 실제로 만들어진 그룹의 입찰 합 × 5 클릭 × 2 (78C naPoolBudgetSync_)
12:59 ③ 매일 주기 (78E naCycleRun_)   최근 10일 실적 받기(78D naPerfFetch_) → 판돈 원장 → 설정 따라잡기 → 줄마다:
                                        보호(리스팅 사라짐·비활성·재고 0·마진 무너짐·판돈 소진 → 멈춤)
                                        → 아마존이 자격을 안 준 것 재시도(3일마다 3주까지)
                                        → 판정(성숙 자료만: 주문 ≥2 이익>0 수익운영 · 주문 1 관찰 · 탐색 14일 끝 주문 0 중단+냉각 28일)
                                        → 탐색 조정(저노출이면 허용 안에서 15% 올림, 3일 간격)
                                        → 인계(성숙 클릭 ≥50 · 주문 ≥3 · 이익>0 → 소유=EXPAND)
                                        → 옛 그룹 청소 (같은 SKU 가 다른 그룹에 켜져 있으면 멈춤)
```
**핵심 식 (78B).** `G = 판매가 × 마진율` (마진율은 수수료·배송비·조달비를 뺀 순수 비율) · `q = 시드 주문율 0.02` (자기 집단 성숙 클릭 500 넘으면 실측으로) · `허용입찰 = min(최대 유효입찰, G × q × 이익보존계수)` · `시작입찰 = 허용 × 시작 비율` · `판돈 = min(상한, G × 탐색배수)`.

**설정 (새 파일 `설정` 탭, 2026-09-15 본격 운영값).** 모드 자동운영 · 주간 시작 상품군 1,000 · 주간 지출한도 ¥300,000 · 판돈 상한 ¥1,000 · 탐색배수 1.0 · 시드 주문율 0.02 · 이익보존계수 1.0 · 시작 비율 1.0 · 탐색 활성일 14 · 냉각 28 · 상품군당 옵션 1 · 옵션 가격대 110% · 풀당 그룹 20 · 판정 유지 주문 2 · 인계 클릭 50 · 인계 주문 3 · 인계 켜기 TRUE. 시험 기간(9/11~9/15)엔 0.5/0.5/0.7 이었고 노출이 안 붙어 올렸다 (기획서 §8.3b). **설정을 바꾸면 도는 줄도 따라간다** (`naPolicyCatchUp_`: 허용 다시 셈, 입찰이 허용×시작비율 아래면 올림, 판돈은 키우기만).

**소유권.** `상품통합` 의 [소유] 칸: `NEW_ADS` 만 프로그램이 건드린다. `EXPAND` 는 인계된 것. 사람이 적은 값은 손대지 않는다. 다른 캠페인에 이미 있는 SKU 는 `제외 · 이미 광고 중` (454개 — 기존 광고 몫).

**시간 예산.** 한 실행 270초, 실행 슬라이스 70초(`ADS_SOFT_MS` 를 잠깐 덮어씀), 꼬리 30초. `withLock_` 로 잠그고, 잠금이 바쁘거나 시간이 다 되면 `ADSPEND_PENDING` 을 돌려 3분 뒤 최대 4번 다시 온다 (`adSchedRun_`). **매일 핸들러에 `withLockOrRetry_` 를 쓰면 안 된다** — 그것은 이어달리기용이라 매일 트리거를 지운다.

### 2.2 🔁 기존 광고 (EXPAND) — `72AA~72AH`

**목적.** 이미 광고 중인 SKU 의 수익을 키운다. 순서가 정해져 있다: **멈춤(돈만 새는 것) → 감액(상한 넘는 것) → 증액 시험(더 써도 되는 것) → 승격(몰아넣기 그룹에 갇혀 값을 못 바꾸는 것을 가격선 캠페인으로)**. 기획서는 `00_기획서.gs` 와 옛 인수인계서 4장.

**왜 '시험' 인가 (72AE).** 입찰을 올리면 광고매출은 거의 언제나 는다. 그것이 이익인지는 되돌려 봐야 안다. `기준 14일 → 올린 값 14일 → 되돌림 → 성숙 16일 → 판정`. 적격 상품군의 20% 는 대조군으로 안 바꾼다. 판정(72AF)은 부트스트랩 구간의 아래끝이 최소 유의미 이익을 넘을 때만 '확대유지'. 양쪽 30개 미만이면 확증 안 함.

**흐름.**
```
월 09:49 후보 다시 세우기 (72AB buildAdExpandCandidates, 72AD buildAdStopCandidates)
          광고실적(SKU×날짜, 성숙 45일 창) × 마진(72AA) × 상품광고목록 → 광고확대후보 [판정]:
          유지 / 시험중 / 증액 시험 / 감액 / 대조군 / 분리 필요 / 천장 / 멈춤·확실 / 멈춤·기대값
사람      광고확대후보 에서 [승인] 체크 → ② 시작 (72AG startAdActions)
          1 멈춤 줄 → 상품광고 낱개 멈춤  2 감액 → 한 계단 내림  3 증액 시험·대조군 → 광고확대시험 표에 세우고 시험군만 올림
          4 분리 필요 → 가격선 캠페인 'KP EXPAND B{k}[T]' 로 승격(72AH)  5 매일 걸음 걸기
매일 08:30 확대 시험 주기 (72AE adExpandCycle) 운영기 끝난 시험 되돌림 · 성숙한 시험 판정 · 승격 뒷정리(옛 그룹 멈춤)
```
**멈춤 근거 (72AD).** `필요 주문율 = CPC ÷ (판매가×마진율)`, `기대 주문율 = (주문+1)÷(클릭+2)`, `상한 = (주문 + 2√(주문+1) + 1) ÷ 클릭`. 상한 < 필요 → '확실', 기대값 < 필요 → '기대값'. 둘을 나눠 적고 나눠 승인.

**신규와의 경계.** 🆕 가 넘긴 SKU(`소유=EXPAND`)는 `adsKeepSkus_` 가 광고실적에 남기고(`naHandedSkus_`), 후보 세우기가 '증액 시험' 으로 받는다. KP NEW 그룹은 1 SKU 라 전용가능.

### 2.3 🌱 새 상품 키우기 (옛 트랙 B) — `72O` `72S` `72Y` `72V_작업큐` `72W` `72Q`

**목적.** 사람이 고른 SKU 몇 개에 **일부러 손해를 보며 키워드 순위를 산다.** 이름이 '새 상품' 이지만 대상은 사람이 고른 것이면 무엇이든. 잘 팔리는 상품의 수동(키워드) 광고도 이 프로그램이다.

**식 (72O adGrowCalc_).** `손익분기CPA = 가격×마진율` · `CPC상한 = CPA×전환율예측` · `시작입찰 = 상한×손해배수 r` · `주간광고비 = 주간허용손해 × r/(r−1)` · `하루예산 = 주간광고비/7`. r=1.5 면 광고비는 허용손해의 3배. **r 은 1보다 커야 한다** (1 = 손해 0 = 기존 광고의 일).

**흐름.**
```
① 키울 상품 등록 (72O addAdGrowSku)   SKU 붙여넣기 → 리스팅에서 ASIN·이름·가격 → 광고육성 에 줄 + 추천값(마진율·전환율·허용손해)
② 값 확인하고 승인 (72Y openAdGrowInputs)  빈칸 추천값 채움 + 위 식 계산해 CPA·상한·시작입찰·주간광고비 적음 → 사람이 [승인]
③ 시작 (72Y startAdGrow)             매일 걸음 걸고 지금 한 번 돌림
매일 05시 한 바퀴 (72O/72S/72V/72W)   계산 → 상태 점검(단계·여력·멈춤필요) → 작업 큐(광고작업) → 실행(자동운영 줄만)
매일 06시 자동 진행 (72Y)             기준키워드 고르기(제 캠페인의 검색어 중 '판 말') → 자동→수동 갈아타기 → 만들기 → 겨냥 좁히기 → 켜기
매일 07시 작업 검증 (72W)             보낸 값이 04시 구조 수집과 같은가 (하루 늦게 '완료' 로 바뀐다 — 정상)
```

## 8. 개발·배포·시험

- **원본은 Apps Script 프로젝트** (스크립트 ID 는 `tools/gs/sc.py` 상수). 저장소 `apps-script/` 는 거울. 고치면 둘 다.
- **배포**: `tools/gs/push.py` — `tools/gs/src/` 의 파일 전부를 Apps Script API `projects.updateContent` 로 밀어 넣는다(부분 배포 없음). 절차: `cp apps-script/*.gs tools/gs/src/ && python3 tools/gs/push.py`. 자격: 같은 폴더의 `client_secret.json`·`token.json` (Google OAuth, **저장소에 없음** — `.gitignore`). 없으면 Apps Script 편집기에 붙여넣어도 된다.
- **시트 읽기·쓰기**: `tools/gs/gs.py` (`read('탭!A1:C')`, `write`, `batch`). 새 파일은 `gs.SS = '<ID>'` 로 바꿔서.
- **원격에서 함수 실행은 못 한다.** 사람이 메뉴를 누르거나 트리거를 기다린다. 결과는 `로그` 탭(`log_`)·`광고변경대장`·알림창으로 본다.
- **시험**: `tools/sim/` — node 로 `.gs` 를 그대로 `eval` 하고 시트·API 를 가짜로 둔다. 전부 돌리기: `cd tools/sim && for f in *.js; do node $f | tail -1; done`. `integ.js` 는 전 파일을 적재해 정의 안 된 호출을 잡는다 (배포 전 반드시). `live_*.js` 는 실자료 덤프(`live2.json`, 30MB — 저장소엔 없음, `live_src.js` 로 다시 받는다)가 필요하다.
- **확인 순서**: 시뮬 전부 통과 → `integ.js` → 배포 → 사람이 메뉴로 실제 실행 → `로그`·표 확인 → 고침. 실제 시트에서만 보이는 것(타임아웃·6분·시트 서비스 타임아웃)이 많다 — 시뮬 통과가 끝이 아니다.
- **커밋**: 한 가지 고침에 한 커밋, 메시지에 "왜". 모델 이름 금지. 가지는 `claude/spreadsheet-manipulation-qysp1q`.
