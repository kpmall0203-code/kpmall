# 신규 등록 상품 광고 자동 배분·운영 시스템 — AI 구현 기획서

버전: NEW-ADS-1.2 / 개정일: 2026-09-10 / 프로그램 식별자: `NEW_ADS`
원본: NEW-ADS-1.0 (2026-09-10). 1.1 은 실제 시트·코드·자료를 확인해 고쳤고, 1.2 는 사용자 확인 넷을 반영했다 —
바깥 시트의 배송비는 예측값이니 그대로 쓸 것 · 마진율의 분모에 배송비가 들어 있을 것 · 돈 한도는 기본값을 넣을 것 ·
주간 한도로 수익 광고를 끄지 말 것.
처리량 기본값은 그 뒤 사용자가 **주 1,000 상품군**으로 확정했다 (§0-G · §8.1 · §8.4).

실행 환경: Google Sheets + Google Apps Script. 산출 대상: 이 문서를 읽은 다른 AI가 구현할 실제 프로그램.

## 1. 이번에 만들 것

**앞으로 등록되는 하루 수백 SKU 의 광고를 자동으로 배분하고 계속 관리하는 시스템.** 지금 사람이 새 상품 리스트를 받아 `ad for x and tiktok` 에 ¥5 로 넣는 손 작업을 대체한다.

사용자는 한국에서 조달해 일본으로 FBM 판매한다. 마진이 낮고(신규 507개 중앙 17.1%) 장기 육성 목적이 없다. 목적:

> 새 상품이 `상품 목록` 에 오르면 시스템이 상품과 옵션을 가르고, 마진으로 감당 가능한 입찰을 셈한 뒤 일부부터 광고한다. 수익 근거가 쌓이면 기존 확대 프로그램(EXPAND)의 사다리에 넘기고, 근거가 없거나 돈이 아까우면 감액·중단한다. 사람이 SKU 마다 손대지 않는다.

'광고하지 않음' · '지금은 대기' · '옵션 중 하나만' 도 정상 결과다.

사용자 화면의 버튼은 정확히 둘이다.

1. **광고할 물건 가져오기**
2. **실행하기**

EXPAND(기존 광고의 멈춤·감액·증액 · 2026-09-10 실운영 시작)와의 관계: **같은 SKU 는 한 프로그램만 만진다.** NEW_ADS 는 신규 상품을 첫 수익 근거까지 데려가고, 그 뒤의 증액 사다리(10% 시험 · 대조군 · 판정)는 EXPAND 가 이미 갖고 있으므로 넘긴다(§7.2). EXPAND 가 꺼져 있으면 NEW_ADS 가 유지 단계에 머문다.

## 3. 사용자 화면

### 3.1 기본 화면

기존 운영 시트의 메뉴 `📣 광고` 아래 `🆕 신규 상품` 하위 메뉴에 두 항목. 결과 표는 새 파일의 `신규광고` 탭(요약)과 `상품통합`(상품별). HTML 사이드바는 만들지 않는다 — 기존 프로그램과 같은 메뉴·알림창 방식.

```
🆕 신규 상품
  ① 광고할 물건 가져오기      상품 목록에서 새 SKU 읽기 · 옵션 묶기 · 마진 · 배분 판정 (돈 안 나감)
  ② 실행하기                 배분대로 캠페인에 넣고 매일 저절로 돌게 (자동운영 + 한도 있을 때만)
```

②의 알림창에 '소액 시작 N · 옵션대기 N · 예산대기 N · 광고제외 N · 정보대기 N · 하루 예산 합계 ¥N · 이번 주 탐색 예약 ¥N / 상한 ¥N' 을 먼저 보이고 [예]를 받는다.

### 3.2 광고할 물건 가져오기

원본은 하나다: 외부 시트 `1ZOgOkmI53oebHB_8rkiYNV4Fk67el6P9SYGOtq2M6-4` 의 `상품 목록`.

| 열 | 내용 | 쓰임 |
|---|---|---|
| A | 소싱지 URL | 상품군키 보조 |
| B | 가격 (KRW, "8,000원") | **조달비** |
| F | 수집 일시 | 가져오기 커서 |
| G | 상품명 (일본어) | 표시 · 옛 이름 매칭 |
| I | 판매가 (JPY 세포함) | 판매가 (등록 시점) |
| L | 마진율 (%) | 참고만 (등록 시점 목표 마진) |
| **O** | **(머리글 없음) 아마존 SKU** | **productKey** |
| P | 배송 방식 | 배송비 요율 |

- O열 머리글을 `SKU` 로 적어 달라고 한 번 요청한다. 코드는 머리글이 없어도 O열을 읽는다.
- 커서: 마지막으로 가져온 F열 수집 일시 + 이미 가져온 SKU 집합. F열은 시각까지 있어 같은 날 여러 번 눌러도 중복 없음. `상품통합` 에 있는 SKU 는 변경분(가격·조달비)만 갱신.
- **등록 확인**: O열 SKU 가 운영 시트 `리스팅`(SP-API, 매일 04시 갱신)에 없으면 아직 아마존에 없는 것 → `정보대기 · NOT_LISTED_YET`. 다음 가져오기에 다시 본다. 507개 중 191개가 리스팅에 있었다 — 나머지는 등록 대기 중이다.
- **소유권 검사**: `상품광고목록` 에 그 SKU 의 ENABLED 광고가 이미 있으면(사람이 `ad for x and tiktok` 에 넣었거나 EXPAND 가 보는 것) `광고제외 · ALREADY_ADVERTISED`. NEW_ADS 는 손대지 않는다.
- 이 버튼은 돈을 쓰지 않는다. 6분에 걸리면 커서를 저장하고 이어받기 트리거로 계속한다(기존 `adDataContinue_` 방식).

### 3.3 실행하기

- 첫 실행에서 돈 값(§8.1)이 비어 있으면 알림창에 무엇이 비었는지 적고 멈춘다. 값은 새 파일의 `설정` 탭에 적는다(EXPAND 의 `광고기준` 과 같은 항목/값/설명 3열).
- 모드가 `자동운영` 이고 돈 값이 다 있을 때만 아마존에 보낸다. 기본은 `모의운영` — 계획까지만.
- 반복 클릭은 이미 만든 캠페인·이미 넣은 SKU 를 다시 만들지 않는다(계획 표 이름·SKU 대조, 2026-09-10 에 승격에서 검증한 방식).
- 적용 동작 `운영 / 신규 편입 중지 / 관리광고 중단 / 모의운영` 은 `설정` 탭의 `신규 · 모드` 한 칸으로 둔다. 별도 버튼 없음.

## 4. 상품 종류와 옵션

```
productKey = 셀러SKU                          (O열. 아마존 SKU 와 같다 — 검증됨)
familyKey  = SKU 에서 끝의 "-숫자" 를 뗀 것     (예: 제피르러시아식마-250g-68PO-1..5 → 제피르러시아식마-250g-68PO)
             소싱지 URL 이 같으면 같은 상품군으로 본다. 둘이 어긋나면 familyKey 를 쓰고 매핑확인 표시
variantKey = SKU 그대로
```

관찰된 실제 패턴: 같은 URL · 같은 이름에 SKU 끝자리 -1~-5, 조달비와 판매가가 배수로 늘어난다(외부 시트 `배수변형` 탭). 즉 옵션은 대개 **수량 배수**다. ASIN 은 `리스팅` 에서 붙인다(SKU→ASIN).

### 4.1 대표 옵션

기본은 상품군당 활성 1개. 순서:

1. `리스팅` 에 있고(등록됨) 조달비·판매가가 있고 마진 > 0.
2. 이미 검증된 수익 근거가 있는 옵션 우선(재등록).
3. 근거가 없으면: 고객 결제총액이 가장 낮은 옵션의 110% 안에 드는 것 중 `G × q0` 가 큰 것. 배수 상품은 대개 `-1`(단품)이 뽑힌다 — 의도한 결과다. 묶음이 절대 마진이 크다는 이유로 우선하지 않는다.
4. 동률은 SKU 문자열 순.

나머지 옵션은 `옵션대기`. 대표가 공급 불가(리스팅 재고 0 · 상태 비활성)가 되면 다음 적격 옵션으로. 대표가 `수익운영` 에 들어가고 남은 한도가 있으면 두 번째 옵션(상품군당 최대 2)을 같은 상품군 누적 탐색비 안에서 시작할 수 있다.

## 6. 낮은 마진을 반영한 계산

### 6.1 광고 전 공헌이익 G

```
조달비(JPY)   = B열 KRW × 사내환율 (운영 시트 `환율` 탭 · 매일 갱신)
판매가(JPY)   = 리스팅의 현재 가격 (없으면 I열)        ← 매일 리프라이싱하므로 L열 마진율은 쓰지 않는다
수수료(JPY)   = 요율표 (판매수수료율 × 판매가) — 기존 57_원가.gs 의 계산을 그대로 부른다
배송/포장비   = P열 배송 방식 + SKU원가/배송비조회 요율 (57_원가.gs)
G            = 판매가 − 조달비 − 수수료 − 배송/포장비 − 예상 환불(초기 0)
```

**판매가에 배송비가 이미 들어 있다.** 일본 아마존 FBM 은 送料込み 가 보통이라 I열 판매가는 고객이 내는 총액이다. 그래서 바깥 시트의 마진율도 `마진 ÷ 판매가` 다 (507줄 확인 · 오차 중앙 0.022%p). **G 를 셀 때 고객 배송비를 판매가에 또 더하지 않는다** — 매출 쪽에 이미 있고 비용 쪽에서 우리 배송비를 뺀다. NEW-ADS-1.0 의 `G = 상품대금 + 고객 배송비 − …` 는 이중 계상이라 위 식으로 바꿨다.

**결측 마진에 기본값을 쓰지 않는다.** 조달비가 없으면 `정보대기`. 기존 상품에 쓰는 기본 15% 는 판매 이력이 있는 상품의 근사이고, 신규에는 근거가 없다. L열 마진율은 표시·검증용(G ÷ 판매가와 5%p 이상 어긋나면 `MARGIN_MISMATCH` 표시)이다.

**바깥 시트의 배송비는 예측값이다** (무게에서 뽑은 것 · 실측 아님). 리프라이싱이 판매가를 바꾸면 그 줄의 배송비를 그대로 두고 수수료만 다시 세어 마진을 고친다(64B). 광고 판단은 그 칸을 쓰지 않고 조달비 + 현재 판매가에서 우리 원가 사슬(57)로 G 를 따로 센다.

### 6.2 주문율 — 시드와 갱신

```
q0 = 신규 시드 (설정 `신규 · 시드 주문율` · 초기 제안 0.02 · 확정 필요)
k  = 50
q  = (O + k × q0) / (C + k)              C·O = 이 SKU 의 성숙 클릭·주문
손익분기 CPC = G × q
허용 유효입찰 = min(G × q × 0.50, 최대 유효입찰 ¥100)
```

**q0 를 계정 평균(3.75%)으로 두지 않는다** (§0-C). 갱신 규칙: NEW_ADS 가 만든 캠페인의 성숙 클릭이 합계 500 을 넘으면 그 집단의 실측 주문율을 다음 q0 로 쓴다(경제성 구간별로 500 이 차면 구간별). 갱신은 `설정` 탭에 값·표본·날짜를 적고, 사람이 고쳐 둔 값이면 덮지 않는다.

시드 2% 에서의 시작 입찰(507개 실측 분포): 10% ¥4.3 · 중앙 ¥5.3 · 90% ¥9.5. 즉 지금의 ¥5 근처에서 시작하되 마진이 큰 것은 더 높게, 작은 것은 더 낮게.

성숙: 클릭일 + 14일 + 지연 2일 (코드가 `sales14d`·`purchases14d` 를 쓴다 — EXPAND 와 같은 정의).

### 6.3 시작 입찰

```
시작 유효입찰 = 허용 유효입찰 × 0.70,  ¥0.01 단위로 내림,  최소 ¥2
```

풀 캠페인의 그룹 = SKU 하나이므로 이 값이 그대로 그룹 기본입찰이다. 배수·위치 가산은 0.

## 7. 광고 시작 이후

매일 [신규 주기](§11)가 돈다. 순서: 보호(가격·조달비 변경 → 상한 재계산 → 넘으면 감액/정지 · 리스팅 비활성 → 정지 · 상품군 탐색비 소진 → 정지) → 결과불명 해소 → 탐색 조정 → 판정 → 인계.

### 7.1 소액 탐색 (근거 없는 상품)

- 활성 기간 최대 14일. 상품군 탐색비 = `min(설정 상한, G × 0.50)`(설정 `신규 · 상품군 탐색배수`). 먼저 소진되면 즉시 정지.
- 저노출(최근 3개 완료일 노출 300 미만 · 클릭 5 미만)이고 상한 여유가 있으면 72시간마다 최대 15% 인상. 누적 노출 1,000 · 클릭 0 이면 인상을 멈추고 `LOW_RELEVANCE` 표시.
- 20클릭 규칙 없음. 만료·소진이면 정지하고 마지막 클릭의 성숙(16일)을 기다린 뒤 판정.
- 정지한 SKU 를 새 캠페인·새 시험ID 로 바꿔 탐색비를 초기화하지 않는다.

### 7.2 유지 → 인계

| 판정 | 조건 (성숙 자료) | 처리 |
|---|---|---|
| `수익운영` | 주문 ≥ 2 · 광고귀속 공헌이익 > 0 · 실제 CPC ≤ 허용 상한 | 그대로 유지. 입찰 변경 없음 |
| `인계` | 클릭 ≥ 50 · 주문 ≥ 3 · 공헌이익 > 0 (EXPAND 의 증액 바닥값과 같다) | **EXPAND 에 넘긴다.** `프로그램소유권` 을 EXPAND 로, 캠페인은 그대로(전용 그룹이라 EXPAND 의 사다리가 바로 쓸 수 있다). 탐색비 원장은 남긴다 |
| `관찰` | 주문 1 | 원래 한도 안에서 유지 |
| `정지` | 만료·소진 뒤 주문 0, 또는 이익 < 0 이 성숙 자료로 확인 | 정지. 냉각 28일 |

인계 뒤에는 NEW_ADS 가 그 SKU 를 만지지 않는다. EXPAND 의 반반 시험·10% 사다리·손실한도가 이어받는다. EXPAND 가 `모의운영` 이면 인계 대신 `수익운영` 에 머문다.

### 7.3 정지 후 재검토

냉각 28일. 조달비·판매가·배송 방식이 바뀌어 G 가 20% 이상 달라지면 재검토. 날짜만으로 재시작하지 않는다. 정지 SKU 의 캠페인 그룹은 PAUSED 로 두고 지우지 않는다.

| 신규 · 이익보존계수 | 0.50 | 0.50 |

**기본값의 근거 (사용자가 위임 · 언제든 고칠 수 있다):**

**처리량 1,000/주** — 앞으로 새로 들어오는 광고가 전부 이 프로그램을 거치므로, 도착하는 상품군(주 700~1,000)을 사실상 전부 받는 수다. 사람이 손으로 `ad for x and tiktok` 에 넣던 일을 그대로 대신한다. 여기서 막히는 일은 도착이 평소보다 많은 주에만 생긴다.

**돈은 '예약' 이 아니라 '실지출' 로 잰다.** 1,000개에 판돈(평균 ¥400)을 미리 다 잡으면 주 ¥400,000 이 필요한데, 실제로는 그만큼 쓰지 않는다 — 지금 신규 SKU 가 들어가는 `ad for x and tiktok`(SKU 12,463개)이 주 **¥101,873** 을 쓴다. 새 상품은 클릭이 잘 안 붙어 판돈을 다 태우는 일이 드물다. 그래서 주간 한도는 **이번 주에 실제로 집계된 NEW_ADS 지출 + 아직 보고 안 된 2일치 준비액**과 견준다.

**¥120,000/주** 는 지금 그 손 작업이 쓰는 ¥101,873 보다 조금 위다 — 대체하면서 목이 졸리지 않게. 계정 전체는 주 ¥258,568 이고 그중 신규 몫이 저것이다.

두 한도의 역할이 다르다:
- **주 1,000개** — 도착을 거의 다 통과시키는 수. 도착이 그보다 많은 주에만 `예산대기 · WEEKLY_CAP` 로 다음 주에 줄 선다.
- **주 ¥120,000** — 안전망. 예상보다 클릭이 많이 붙어 지출이 튀면 그 주의 새 시작을 멈춘다. 평소에는 안 걸린다.

**상품군 판돈 ¥1,000** 은 천장이고 실제로는 `G × 0.5` 가 먼저 걸린다 — 신규 507개 기준 평균 ¥400 · 중앙 ¥354. 시작 입찰 ¥5.3 이면 약 70클릭, 주문율 2% 면 기대 주문 1.4건. 팔릴 것을 증명하는 크기가 아니라 **아무 반응 없는 것을 싸게 걸러내는 크기**다.

### 8.2 배분 순서

**주간 상한은 '새로 시작하는 것' 만 막는다. 이미 수익을 내는 광고는 이 상한 때문에 끄지 않는다.**

수익이 나는 광고는 제 밥값을 하고 있다 — 예산을 맞추려고 그것을 끄면 벌던 돈을 버리고 한도만 지킨다. NEW-ADS-1.0 §8.2 는 "필요액이 가용액보다 크면 수익 여유가 낮은 상품부터 감액/중단한다" 고 썼는데, 그 규칙을 뺀다. 같은 이유로 EXPAND 도 오늘(2026-09-10) 손실한도를 '전부 되돌림' 에서 '손해를 내는 시험만 되돌림' 으로 고쳤다.

수익 광고가 멈추는 경우는 셋뿐이고, 셋 다 예산이 아니라 **그 광고 자신의 성적**이다:
- 성숙 자료로 이익이 음수가 됐다 (→ 감액, 그래도 음수면 중단)
- 가격·조달비가 바뀌어 실제 CPC 가 새 허용 상한을 넘었다 (→ 허용 상한까지 감액)
- 리스팅이 비활성·품절이 됐다 (→ 정지)

순서:

1. **이번 주 NEW_ADS 실지출**(광고비원장에서 트랙 N 캠페인만) + 아직 보고 안 된 2일치 준비액을 센다. 예약액을 쌓지 않는다 — 판돈은 상품군마다 제 원장에서 지키므로(§8.3) 주간 주머니에서 미리 뺄 필요가 없다.
2. 그 값이 **주간 지출한도**를 넘었으면 이번 주에는 새 상품군을 시작하지 않는다. **이미 도는 것은 그대로 둔다** — 수익 광고도, 탐색 중인 것도.
3. 안 넘었으면 **주 시작 상품군 수**(기본 1,000) 안에서 새로 시작한다. 이번 주에 이미 시작한 수를 빼고 남은 만큼만.
4. 고르는 순서: 재등록 근거 있음 → `G × q0` 큰 순 → 같은 등급에서 오래 기다린 순. 시작 슬롯의 10% 는 `G × q0` 하위에도 준다(누적 쿼터).
5. 상품군 안의 옵션 비용은 합산한다.

가용액이 모자라 시작을 못 한 상품군은 `예산대기 · WEEKLY_CAP` 이고, 다음 주에 다시 줄 선다.

### 8.3 원장

```
이번 주 쓴 돈 = 트랙 N 캠페인의 집계 지출 + 최근 2일 준비액
새 시작 가능  = (이번 주 쓴 돈 < 주간 지출한도) 이고 (이번 주 시작 수 < 주 시작 상품군 수)

상품군 위험손실   = max(0, 상품군 누적 탐색 광고비 − 성숙 광고귀속 공헌이익)
상품군 남은 판돈  = min(상품군 판돈 − 누적 탐색비, 상품군 판돈 − 위험손실)
                    ← 0 이 되면 그 상품군의 탐색을 멈춘다 (§7.1)
```

판돈은 **상품군 하나의 평생 한도**이고 주간 주머니에서 미리 빼지 않는다. 이렇게 나눈 이유: 1,000개를 미리 예약하면 주 ¥400,000 이 잠기는데 실제 지출은 그 몇 분의 일이라, 예약 방식은 쓰지도 않을 돈으로 시작을 막는다.

원장은 기존 `광고비원장`(72R) 과 `광고변경대장`(72F) 을 쓴다 — 새로 만들지 않는다. 상품군 누적은 새 파일 `상품군광고` 에.

### 8.4 처리량

하루 473 SKU ≈ 상품군 100~150 → 주 700~1,000. 기본값 주 1,000 이면 사실상 전부 받는다.

동시 활성 탐색 ≈ 1,000 × (14일 ÷ 7일) = **약 2,000 광고그룹**(그룹당 SKU 하나). 캠페인 풀 20그룹이면 **캠페인 약 100개**가 동시에 돈다. 지금은 캠페인 39 · 그룹 65 이므로 **자원이 31배로 는다.**

이 규모는 §15.2 의 부하 확인을 통과해야 켠다. 확인할 것: 매일 주기가 2,000 그룹의 상태·실적을 6분 안에 훑는가(못 하면 커서로 나눠 돈다), 아마존 계정의 캠페인·그룹·상품광고 한도, 하루 API 호출 수, 새 파일의 셀 증가(주 1,000줄 × 30열 = 3만 셀/주 → 1년 156만 셀).

**단계적으로 연다:** 1주차 주 100 → 2주차 400 → 3주차 1,000. 각 주에 매일 주기의 소요시간과 실지출을 보고 다음 주 수를 정한다. 1주차부터 1,000 으로 열지 않는다 — 되돌리기 어려운 규모다. 기본값이 1,000 이라는 것은 '3주차에 도달할 자리' 라는 뜻이고, 1주차에는 `설정` 탭에서 100 으로 낮춰 시작한다.

## 9. 캠페인 구조

### 9.1 풀

```
캠페인 이름 = KP NEW B{k}-{n}     k = 목표 CPC 가격선(기존 adPromoBand_: ¥2 × 1.5^k) · n = 풀 번호
광고그룹    = SKU 하나            그룹 기본입찰 = 그 SKU 의 시작 유효입찰
캠페인당 그룹 20개 (설정) · 넘치면 n+1
```

가격선으로 묶는 이유는 EXPAND 승격(72AH)과 같다 — 비슷한 값을 부를 것끼리 한 캠페인의 일예산을 나눠 쓴다. 그룹을 SKU 하나로 두는 이유는 §6.3 — 입찰이 SKU 마다 다르고 나중에 EXPAND 사다리가 그룹 단위로 올린다. 캠페인 일예산 = 그 캠페인 그룹들의 (시작입찰 × 예상 하루 클릭 5) 합 × 2, 최소 ¥100.

인계된 SKU 는 캠페인을 옮기지 않는다. 캠페인 이름의 `NEW` 가 남아 있어도 소유권 표가 진실이다.

### 9.2 만들기·정지

기존 72J(`adPlanExecStep_`)가 만든다 — 계획 표 `광고생성계획` 에 트랙 `N` 으로 줄을 넣는다. 72J 는 2026-09-10 에 부분 성공·옛 광고 검색·ID 저장 문제를 고쳤다. 만든 뒤 `상품광고목록` 에 그 SKU 의 다른 ENABLED 광고가 있으면(사람이 tiktok 에도 넣은 경우) 그것을 멈춘다 — 승격 뒷정리(`adPromoteStopOld_`)를 트랙 N 에도 적용한다. 매일 주기에서도 같은 검사를 한다.

### 9.3 수동 캠페인

만들지 않는다(초기). 인계 뒤 EXPAND/검색어 프로그램(72L·72P)이 판단한다.

## 10. 자료 수집

- **신규 캠페인의 SKU 별 일별 실적을 전량 받는다.** 지금 수집(`scheduledAdsSpend`)은 지출 상위 2,000 SKU 만 받으므로 신규 SKU 는 거의 빠진다. 같은 리포트 요청에 `campaignIdFilter`(트랙 N 캠페인 ID)를 걸어 하루 한 번 따로 받고 새 파일 `신규광고일별` 에 적는다. 열은 `광고실적` 과 같다(날짜·SKU·ASIN·캠페인·광고비·광고매출·노출·클릭·주문).
- 구조·상품광고목록·지출원장은 기존 수집이 계정 전체를 받으므로 그대로 쓴다.
- 리스팅(가격·재고·상태)은 매일 04시 SP-API 갱신을 쓴다. `등록일` 탭은 open-date 라 며칠 늦을 수 있어 등록 확인에는 `리스팅` 존재 여부를 쓴다.
- 성숙 = 클릭일 + 16일. 최근 16일은 잠정으로 표시하고 판정에 쓰지 않는다.

## 11. Apps Script 실행 구조

코드는 **기존 프로젝트**(`1bfe6yklrT_KPjYznBDT4_InHZBY7SionvWaj5e9B9UIAa27ORfozew9I`)에 `78_신규광고_*.gs` 로 둔다. 자격증명·API 층(72_광고)·대장(72F)·캠페인 생성(72J)·상품광고목록(72AC)·원가(57)·환율(50)·가격선(72AH)·재개 가능한 걸음(72X)을 그대로 쓴다. 새 파일에는 코드를 두지 않는다(빈 프로젝트 `1OG2o…` 는 손대지 않는다).

```
① 가져오기  newAdsImport()      상품 목록 읽기 → 리스팅 대조 → 상품군 → G → 배분 → 상품통합/상품군광고 쓰기
② 실행      newAdsRun()         정책 확인 → 예약 → 계획 표(트랙 N) → 72J 로 만들기 → 뒷정리 → 걸음 걸기
매일        scheduledNewAdsCycle()  보호 → 결과불명 → 탐색 조정 → 판정 → 인계 → 뒷정리   (10시 · 트리거 12번째)
```

트리거는 하나만 더한다(지금 11개, 한도 20). 신규 실적 수집은 기존 `scheduledAdsSpend` 에 두 번째 요청으로 붙인다.

6분 규칙: 모든 걸음은 210초에 커서를 저장하고 이어받기 트리거를 건다. 아마존에 보낸 뒤 시트에 적기 전에 끊기지 않도록 20건마다 적는다(EXPAND 와 같은 방식).

작업키 `N|SKU|자원|동작|목표값`. 상태 `대기/예약/실행중/검증대기/완료/재시도/결과불명/취소/보호중단`. LockService 는 예약과 짧은 상태 전이에만.

## 14. 이행

1. **손 작업을 멈춘다.** 새 상품 리스트를 `ad for x and tiktok` 에 넣는 것을 `cutoverAt` 부터 하지 않는다. 대신 ① 가져오기를 누른다(같은 리스트가 `상품 목록` 에 있다).
2. `cutoverAt` 이전에 등록된 SKU(tiktok 12,463개 포함)는 EXPAND 가 계속 본다. NEW_ADS 는 `상품통합` 에 없는 SKU 만 다룬다.
3. 실수로 또 넣어도: ① 에서 `ALREADY_ADVERTISED` 로 걸러지고, 이미 NEW_ADS 가 시작한 SKU 면 매일 주기가 tiktok 쪽 광고를 멈춘다(§9.2).
4. `상품 목록` O열 머리글을 `SKU` 로. 조달비 B열이 "8,000원" 같은 글자이므로 숫자로 파싱(쉼표·원 제거).
5. 외부 시트 읽기 권한: 기존 72AA 가 이미 같은 파일의 `광고 기준값`·`상품 목록` 을 읽는다. 추가 권한 없음.
6. API 키·OAuth 비밀값은 스크립트 속성에만. 시트·문서·로그·커밋에 복사하지 않는다.

## 15. 구현 순서와 완료 기준

### 15.1 순서

1. 72AA 마진 문맥에 `상품 목록` O열 SKU 매칭 + B열 조달비 → G 재계산 추가. **EXPAND 에도 바로 이득**(기본값 211개 중 앞으로 등록되는 것은 실측을 쓴다).
2. 새 파일에 `설정`·`상품통합`·`상품군광고` 만들기, ① 가져오기 (모의).
3. 배분·대표 옵션·시작 입찰 모의 계산 → 시작 입찰 분포 확인(§6.2 표와 견줌).
4. ② 실행: 계획 표 트랙 N → 72J → 뒷정리. 신규 실적 전량 수집.
5. 매일 주기: 보호·탐색 조정·판정·인계.
6. 소액 실범위(상품군 10개)에서 시작/정지/인계 확인 → 자동운영.
7. q0 갱신(§6.2)·옵션 추가·부하 확인.

### 15.2 필수 검증 (시뮬레이터 + 실제 자료)

- 두 버튼만으로 가져오기·시작·일상 운영. 반복 클릭에 중복 없음.
- 507개 실자료로: 마진 ≤ 0 → 제외, 배수 옵션 → 단품이 대표, 시작 입찰 분포가 §6.2 와 일치.
- `ad for x and tiktok` 에 이미 있는 SKU → `ALREADY_ADVERTISED`. NEW_ADS 시작 뒤 사람이 또 넣으면 → 다음 주기에 멈춤.
- 6분 끊김: 아마존에 보낸 것은 반드시 표에 있다(20건마다 저장).
- 부분 성공: 아마존이 일부만 돌려주면 그 SKU 만 성공으로, 나머지는 `결과불명`.
- 돈 값이 비면 시작하지 않는다. 주간 상한을 넘으면 `예산대기`.
- 인계: EXPAND 의 `광고확대후보` 가 다음 주 그 SKU 를 자기 것으로 본다(소유권 표).
- 부하: 상품군 100·500 동시 활성에서 매일 주기 소요시간·API 호출 수.

### 15.3 완료물

실행 가능한 `.gs`(기존 프로젝트) · 새 파일 스키마 · 두 메뉴 항목 · 시뮬레이터 결과 · 실자료 모의 결과 · 정책 입력 안내 · 장애/중단/복원 안내.

## 16. 5엔보다 나아졌는지

지표: 광고 차감 공헌이익 · 불필요한 탐색비 · 상품군당 광고비 · 자동 처리 비율. 광고매출만으로 결론내리지 않는다.

비교 실험은 **EXPAND 의 반반 시험**(같은 ASIN 은 같은 편 · 차이의 차이 · 부트스트랩 구간 · 상품군 30개 이상)을 그대로 쓴다. 파일럿 기간에 적격 상품군을 반으로 나눠 절반은 NEW_ADS, 절반은 기존 ¥5 손 작업으로 4주 돌리고 같은 기간 공헌이익을 견준다. 이익이 안 나는 상품을 실험 때문에 계속 광고하지 않는다.

## 17. 구현 AI 에게

> 이 문서(1.1)를 최신 요구로 삼아 기존 Apps Script 프로젝트에 NEW_ADS 를 구현하라. 원본은 외부 시트 `상품 목록` 한 탭(O열 SKU · B열 조달비 KRW)이고, 등록 확인은 운영 시트 `리스팅` 으로 한다. 신규 표는 새 파일 `Amazon 신규 상품 광고` 에 두고 코드는 기존 프로젝트에 둔다. q0 는 계정 평균이 아니라 시드 2% 에서 시작해 실측으로 갱신하라. 결측 마진에 기본값을 쓰지 마라. 이미 광고 중인 SKU 는 건드리지 말고, 첫 수익 근거가 서면 EXPAND 에 넘겨라. 돈 값이 비어 있으면 모의운영까지만 완성하라. 시뮬레이터(`scratchpad/sim`)와 507개 실자료로 검증 결과를 제출하라.
